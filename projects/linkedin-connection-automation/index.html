LinkedIn Connection Automation

Five n8n workflows that scrape, enrich and personalise LinkedIn outreach end to end.

Role
Automation Engineer
Category
Automation
Timeline
2 weeks

Overview

An outbound pipeline built for an agency CEO who was sourcing prospects by hand: pull leads out of LinkedIn Sales Navigator, enrich them with real profile detail, store them, write a connection note that actually references the person, and send the request.

Rather than one large flow that does everything, the system is five separate n8n workflows, each owning a single job and handing off through the database. That split is the design decision the whole build rests on — a scrape can fail without taking the sending stage down with it, and any stage can be re-run against the rows already in Supabase without re-scraping anything.

My Role

Sole builder. I designed the workflow split, chose and wired the Apify actors, modelled the lead schema in Supabase, wrote the prompt and routing for note generation through OpenRouter, and ran the pipeline against the client's own Sales Navigator account under their supervision.

Key Features

Five workflows, one job each.

1 · Lead scraping
An Apify actor runs a saved LinkedIn Sales Navigator search and returns the matching leads as structured rows rather than a page of HTML.
2 · Profile enrichment
A second actor takes each lead and pulls the fuller profile — headline, current role, company, recent activity — so the note has something specific to work with.
3 · Storage and deduplication
Everything lands in Supabase keyed on the profile, so re-running a search doesn't create duplicates and every lead carries its own status through the pipeline.
4 · LLM note generation
OpenRouter generates the connection note per lead from the enriched profile, kept inside LinkedIn's character limit and written to reference something real about the person.
5 · Connection sending
The final workflow sends the request with its generated note and writes the outcome back to the row, so state lives in the database rather than in a workflow's memory.

Challenges & Solutions

The problems that shaped the build, and what I did about them.

A single flow makes every failure total

Scraping, enriching, generating and sending in one workflow means a rate limit at step two throws away the work already done and leaves no record of how far it got.

Solution: Split into five workflows that communicate only through Supabase. Each lead carries a status column, so a stage picks up exactly the rows that are ready for it and a failure costs one stage, not the run.

Generic notes are worse than no note

A templated "I'd like to add you to my network" reads as automated and costs the sender more reputation than it wins replies.

Solution: Fed the enriched profile — not just the name — into the model through OpenRouter, and constrained the prompt to cite one concrete detail from the person's actual profile. Notes that couldn't clear that bar were held rather than sent.

Automating someone else's account is a trust problem

The pipeline ran against the client's own Sales Navigator account, where a volume mistake carries a real cost to their professional profile.

Solution: Kept sending rate-limited and human-visible. Every generated note is stored and reviewable before the sending workflow picks it up, so the client could see exactly what was going out under their name.

Results

What shipped, and what changed because of it.

  • Lead sourcing that was being done by hand now runs unattended from a saved Sales Navigator search.
  • Every connection request goes out with a note written against that person's real profile, not a template.
  • Because state lives in Supabase, any stage can be re-run or resumed without re-scraping — a failed run costs minutes, not the whole batch.
